# ПОС — Преподавательская Оценка Студентов

Консольный модуль учёта преподавательской оценки студентов: студенты, рубрикатор критериев, оценки, итог по весам, статистика и экспорт.
Реализован на Go с применением DDD, архитектуры **Ports & Adapters (Hexagonal)** и паттернов GoF.

## Запуск

Требуется Go 1.27+.

```sh
go run . -demo          # сквозной сценарий: студенты и критерии → оценки → итог → экспорт
go run .                # интерактивное меню, данные хранятся в build/pos-data.json
go run . -data my.json  # интерактивное меню с другим файлом данных
go test ./...           # юнит-тесты
```

Демо работает на данных в памяти (файл данных не трогает) и выгружает итоги в `build/results.csv` и `build/results.json`.

### Возможности консоли

| Раздел | Пункты |
|---|---|
| Студенты | список, добавить, переименовать, удалить (вместе с оценками) |
| Рубрикатор | список (с долей каждого критерия в итоге), добавить (название, max_score, вес), изменить название/вес, удалить (вместе с оценками) |
| Оценки | выставить, исправить, отменить, посмотреть (по студенту или все) |
| Итоги | итог студента с расшифровкой по критериям, ведомость итогов, статистика по критериям, смена правила итога, экспорт в CSV/JSON |

Идентификаторы назначаются автоматически: студенты `s1, s2, …`, критерии `c1, c2, …`. Балл можно вводить и через точку, и через запятую.

## Предметная область и логика решений

### Ubiquitous Language

Слова из предметной области используются в коде без перевода «на программистский»:

| Термин | В коде | Смысл |
|---|---|---|
| студент | `Student` | кого оценивают |
| критерий | `Criterion` | за что ставят балл; есть максимум (`MaxScore`) и вклад в итог (`Weight`) |
| рубрикатор | `Rubric` | набор критериев курса |
| оценка | `Evaluation` | факт «этому студенту по этому критерию поставили такой балл» (+ дата и комментарий) |
| выставить / исправить / отменить оценку | `Grade`, `Correct`, `CancelEvaluation` | сценарии работы с оценкой |
| итог | `FinalGrade` | результат студента, вычисленный из его оценок и рубрикатора |
| правило итога | `GradingPolicy` | как именно из оценок получается итог |

### Ключевые решения

- **Итог по 10-балльной шкале с нормировкой весов:** `итог = 10 · Σ wᵢ·(scoreᵢ / maxᵢ) / Σ wᵢ`.
  Веса не обязаны давать в сумме 1: веса 3 и 2 работают так же, как 0.6 и 0.4. Поэтому добавление критерия не ломает рубрикатор.
- **Итог нигде не хранится.** Он каждый раз вычисляется доменным сервисом из текущих оценок и рубрикатора, поэтому не может разойтись с ними.
- **У студента не более одной оценки по критерию.** Идентичность оценки — пара «студент × критерий». Повторно выставить оценку нельзя: её нужно явно исправить или отменить, чтобы оценку нельзя было случайно перезаписать.
- **Вес критерия менять можно, максимум — нельзя.** Смена веса безопасна, итог просто пересчитается. Уменьшение максимума задним числом сделало бы выставленные оценки некорректными («8 из 5»).
- **Удаление каскадное.** При удалении критерия или студента удаляются и их оценки. Иначе в хранилище остались бы оценки по несуществующему критерию.
- **Данные из хранилища проходят те же проверки, что и ввод пользователя.** Если в JSON-файл руками вписать «12 из 10», модель откажется его загрузить.

## Карта DDD

### Entity и Value Object

**Value Object** — объект без собственной идентичности: два одинаковых значения взаимозаменяемы. Он неизменяем, а проверка выполняется в конструкторе. Все VO — структуры с закрытыми полями, поэтому создать некорректное значение в обход конструктора нельзя.

| Value Object | Инвариант |
|---|---|
| `StudentID`, `CriterionID` | непустой |
| `EvaluationID` | пара (студент, критерий), обе части непустые |
| `FullName`, `CriterionName` | непустое, ≤ 200 символов, лишние пробелы схлопываются; названия критериев сравниваются без учёта регистра |
| `Comment` | ≤ 500 символов, может быть пустым |
| `Score` | конечное число ≥ 0 (верхнюю границу задаёт критерий) |
| `MaxScore`, `Weight` | конечное число > 0 |
| `FinalGrade` | в пределах [0, 10]; создаётся только доменным сервисом |

**Entity** — объект с идентичностью, которая сохраняется при изменении состояния.

| Entity | Идентичность | Почему не VO |
|---|---|---|
| `Student` | `StudentID` | если студент сменит ФИО, это тот же студент, а двое однофамильцев — разные люди |
| `Criterion` | `CriterionID` | переименованный критерий с новым весом остаётся тем же критерием, и оценки по нему сохраняются |
| `Evaluation` | `EvaluationID` | исправленная оценка — та же оценка с другим баллом, а не новая |

> **Пример.** `Score(8)` — Value Object: восьмёрка равна любой другой восьмёрке, и «изменить» её нельзя — можно только заменить другим значением.
> `Evaluation` — Entity: оценка студента `s1` по критерию `c1` после исправления с 8 на 9 остаётся той же самой оценкой (тот же `EvaluationID`), у неё лишь меняются балл, комментарий и дата.

### Агрегаты

| Агрегат (корень) | Состав | Что охраняет |
|---|---|---|
| `Student` | студент | ФИО не пустое |
| `Rubric` | критерии `Criterion` | уникальность ID и названий; критерий существует. Только через рубрикатор можно добавить, изменить или найти критерий; наружу критерии отдаются копиями |
| `Evaluation` | оценка | балл в пределах критерия при создании (через фабрику) и при исправлении (`Correct` снова сверяется с рубрикатором) |

Оценка — отдельный агрегат, а не часть студента или рубрикатора: она ссылается на них по ID. Иначе любое изменение оценки требовало бы загружать и сохранять целиком студента со всеми оценками.

### Инварианты

| Правило | Где охраняется |
|---|---|
| балл не выходит за пределы критерия | `Score` (≥ 0) + `Criterion.CheckScore` (≤ max); вызывается в `EvaluationFactory`, `Evaluation.Correct` и `FinalGradeCalculator` |
| оценку можно выставить только по критерию из рубрикатора | `Rubric.Criterion` в `EvaluationFactory` и `Evaluation.Correct` |
| итог согласован с текущим набором оценок | `FinalGradeCalculator` (Domain Service) считает итог на лету и отказывается считать по чужой оценке, по удалённому критерию или при дубле |

### Repository (порты)

Интерфейсы объявлены в домене ([domain/repository.go](domain/repository.go)), реализации находятся снаружи, в адаптере [adapters/jsonstore](adapters/jsonstore):

- `StudentRepository` — `Save`, `ByID`, `All`, `Delete`;
- `RubricRepository` — `Load`, `Save`;
- `EvaluationRepository` — `Save`, `ByID`, `ByStudent`, `All`, `Delete`, `DeleteByStudent`, `DeleteByCriterion`.

Кроме них домен объявляет порт `Clock`, чтобы не вызывать `time.Now()` напрямую и чтобы дату оценки можно было зафиксировать в тестах.

### Domain Service

`FinalGradeCalculator` ([domain/grading.go](domain/grading.go)) — расчёт итога. Это правило не принадлежит ни одной сущности: итог зависит одновременно от студента, рубрикатора (максимумы и веса) и набора оценок. Перед расчётом сервис проверяет согласованность данных, а сам расчёт делегирует сменяемой политике (см. Strategy).

## Архитектура: Ports & Adapters

```
                ┌──────────────────────── adapters ───────────────────────┐
                │  console (входящий)   jsonstore · export · system (исх.) │
                └──────────────┬───────────────────────────┬──────────────┘
                               │ вызывает входной порт     │ реализуют выходные порты
                               ▼                           ▼
                ┌──────────────────────────── app ────────────────────────┐
                │  Facade (входной порт) · Service (сценарии)             │
                │  ResultExporter (выходной порт)                         │
                └──────────────────────────────┬──────────────────────────┘
                                               ▼
                ┌─────────────────────────── domain ──────────────────────┐
                │  Entity, VO, инварианты, EvaluationFactory,             │
                │  FinalGradeCalculator, порты Repository и Clock         │
                └─────────────────────────────────────────────────────────┘

      Зависимости направлены строго внутрь:  main → adapters → app → domain
```

| Папка | Слой | Содержимое | От чего зависит |
|---|---|---|---|
| [domain/](domain) | ядро | сущности, VO, инварианты, фабрика, доменный сервис, порты репозиториев и часов | только стандартная библиотека |
| [app/](app) | приложение | входной порт `Facade` и его реализация `Service` (сценарии), выходной порт `ResultExporter`, модели для отображения (`*View`) | `domain` |
| [adapters/console/](adapters/console) | входящий адаптер | меню, ввод/вывод, демо-сценарий | `app.Facade` |
| [adapters/jsonstore/](adapters/jsonstore) | исходящий адаптер | JSON-хранилище, реализует три репозитория; маппинг DTO ↔ домен | `domain` |
| [adapters/export/](adapters/export) | исходящий адаптер | экспорт итогов в CSV и JSON, реализует `app.ResultExporter` | `app` |
| [adapters/system/](adapters/system) | исходящий адаптер | системные часы, реализует `domain.Clock` | — |
| [main.go](main.go) | composition root | сборка графа зависимостей в DI-контейнере | всё |

Домен не знает ни про консоль, ни про JSON и CSV. Консоль не знает про хранилище и домен, она работает только с `app.Facade`. Чтобы заменить JSON-файл на базу данных, нужно написать ещё один адаптер репозиториев и поменять его регистрацию в `main.go`. Чтобы добавить HTTP-API, нужен ещё один входящий адаптер к тому же `Facade`.

### DI-контейнер

Граф собирается в [main.go](main.go) с помощью [go.uber.org/dig](https://github.com/uber-go/dig):

- адаптеры регистрируются под интерфейсами портов (`dig.As(new(domain.StudentRepository))` и т. п.), поэтому остальной код получает абстракцию, а не конкретный тип;
- экспортёры собираются в группу (`dig.Group("exporters")`): чтобы добавить новый формат, достаточно зарегистрировать ещё один провайдер, сервис менять не нужно;
- в `main.go` задаётся и список правил итога (первое — правило по умолчанию).

Слои `domain` и `app` про контейнер ничего не знают: зависимости приходят к ним через конструкторы.

## Паттерны GoF

| Группа | Паттерн | Где | Какую проблему решает |
|---|---|---|---|
| Порождающий | **Factory** | `domain.EvaluationFactory` ([domain/evaluation.go](domain/evaluation.go)) | Оценка появляется в нескольких местах: ручной ввод, загрузка из хранилища, в будущем — импорт ведомости. Фабрика — единственная точка создания, где собраны все правила: студент существует, критерий есть в рубрикаторе, балл в [0, max_score]. Без неё проверки пришлось бы повторять в каждом сценарии, и рано или поздно одна из них потерялась бы. Метод `Restore` прогоняет через те же проверки данные из файла. |
| Структурный | **Facade** | `app.Facade` / `app.Service` ([app/](app)) | Чтобы выставить оценку, нужно загрузить студента и рубрикатор, вызвать фабрику, проверить дубль и сохранить; при удалении критерия — ещё и снять оценки по нему. Без фасада эта логика оказалась бы в обработчиках меню. Консоль видит одну точку входа с методами в терминах предметной области (`Grade`, `FinalGrade`, `ExportResults`), а сам фасад служит входным портом гексагональной архитектуры. |
| Структурный | **Decorator** | `domain.RoundedPolicy` ([domain/grading.go](domain/grading.go)) | Как считать итог и как его округлять — два независимых правила. Декоратор добавляет округление (до целого или до N знаков, половина вверх, с поправкой на погрешность float) к любой политике, не меняя её. Без него пришлось бы заводить отдельный класс на каждую комбинацию «правило × округление». |
| Поведенческий | **Strategy** | `domain.GradingPolicy` в `FinalGradeCalculator` | Правило итога меняется в зависимости от ситуации. Для финальной ведомости неоценённый критерий — 0 (`WeightedAveragePolicy`), для промежуточного среза учитываются только оценённые критерии (`GradedOnlyPolicy`). Доменный сервис отвечает за согласованность данных, а формулу берёт из стратегии. Правило переключается прямо из меню. |

Правила итога, доступные в приложении:

1. взвешенное среднее, нет оценки = 0, округление до целого — **по умолчанию** (Strategy + Decorator);
2. взвешенное среднее, нет оценки = 0, без округления;
3. взвешенное среднее по оценённым критериям, округление до 2 знаков.

В демо видно, зачем нужна смена правила: у студента без экзамена итог 4 / 3.6 / 6 в зависимости от правила.

**От чего отказался сознательно:**

- **Builder** для рубрикатора — `Rubric.AddCriterion` уже охраняет все инварианты, а пошаговая сборка ничего бы не добавила.
- **Template Method** для импорта ведомостей — импорта нет в функциональных требованиях, а паттерн без задачи был бы «для галочки».
- Экспорт в CSV и JSON — это два адаптера одного порта, отдельным паттерном я его не считаю.

## Тесты

```sh
go test ./...          # все тесты
go test ./... -cover   # с покрытием
```

| Пакет | Что проверяется |
|---|---|
| `domain` | VO отклоняют некорректные значения; рубрикатор не допускает дублей; фабрика не даёт поставить 12 из 10 и оценить критерий не из рубрикатора; `Correct` сохраняет инварианты; доменный сервис считает итог при разных стратегиях, нормирует веса, отклоняет несогласованные данные; округление в декораторе |
| `app` | сценарии через фасад: выставление, повторная оценка, исправление и отмена, смена правила итога, каскадное удаление, статистика, экспорт |
| `adapters/jsonstore` | данные сохраняются и загружаются из файла; испорченные данные в файле отклоняются |
